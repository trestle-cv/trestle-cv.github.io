Clustering

Run Trestle as an explicitly replicated SQLite cluster.

Trestle clustering uses the shared Gantry Core Raft runtime proven first in Watchpost. It keeps consensus mechanics generic while Trestle owns collection and record semantics.

Initial clustered surface

The first clustered semantic surface is collection definitions and records. Authentication/session state, credentials, files, jobs, webhook and function execution, audit/events, propagation scheduling and other external side effects are not silently copied into consensus; they remain node-local or deferred until they have an explicit distributed contract.

Authority and failure behaviour

standalone                 -> ordinary local writes
replicated ready leader    -> Raft proposal
replicated ready follower  -> authenticated forward to leader
replicated unavailable     -> reject; never fall back to local SQL

Follower writes retain the caller operation identity and wait until the committed index is locally applied before returning.

Configuration

TRESTLE_REPLICATION_ENABLED=true
TRESTLE_REPLICATION_NODE_ID=tr_...
TRESTLE_REPLICATION_LISTEN=10.0.0.10:7440
TRESTLE_REPLICATION_BOOTSTRAP=true
TRESTLE_REPLICATION_TLS_CERT=/etc/trestle/replication.crt
TRESTLE_REPLICATION_TLS_KEY=/etc/trestle/replication.key
TRESTLE_REPLICATION_TLS_CA=/etc/trestle/replication-ca.crt

Production clustering requires the complete cert/key/CA triplet. Plaintext is an explicit local-development opt-in. The initial clustered materialization is SQLite-only; PostgreSQL clustering fails closed rather than presenting an unsafe partial mode.

Operator surface

The production operator path drives explicit Raft membership through the running node: trestle replicate status, trestle replicate join <node-id> <raft-address>, and trestle replicate snapshot (admin session, CSRF-protected). Gantry pairing and Raft voter membership are separate; a paired peer is never silently promoted to a voter.

Membership

Pair every replication participant, then add voters explicitly via trestle replicate join. Disabling or revoking a Gantry peer stops replication authorization in both directions; reauthorizing it allows normal catch-up.

Durability

<data-dir>/
  trestle.db
  replication/
    raft.db
    snapshots/

Use stable node IDs and replication addresses. Do not delete Raft state as an upgrade procedure.

Production deployment and bootstrap

A three-node production cluster is formed from scratch in this order: install Trestle and configure SQLite with replication enabled on every node; publish each node's public HTTPS endpoint and Raft address; deploy the cluster CA and per-node certificates for the Raft transport; initialize the Gantry node identity on every node; fully mesh Gantry pairing so each pair authenticates in both directions (A <-> B, A <-> C, B <-> C); start one node with TRESTLE_REPLICATION_BOOTSTRAP=true and verify trestle replicate status reports a ready leader; then add the remaining nodes as voters explicitly with trestle replicate join <node-id> <raft-address> from the leader and verify all three voters on every node.

The two relationships are deliberately different: Gantry pairing authenticates peers, while trestle replicate join changes Raft voter membership. A paired peer is never silently promoted to a voter, and removing Gantry authorization does not change Raft membership by itself.

CLI environment

Cluster and replication operator commands (trestle cluster ..., trestle replicate ...) read the same environment as the server: they must run against the installed service configuration, not a shell default. On systemd installs the service environment lives in the service's environment file (for example /etc/trestle/trestle.env); run CLI commands with that environment loaded so they target the configured data directory and database. Cluster CLI commands operate on the local node's database directly, while trestle replicate authenticates over the admin API.

TLS and ports

The application HTTPS endpoint terminates TLS in front of the Trestle HTTP server (for example with Caddy) and is the address used as each node's public endpoint and forwarding target. The Raft replication transport listens on TRESTLE_REPLICATION_LISTEN (a node-specific address and port, for example 10.0.0.10:7440) and requires mutual TLS from the cluster CA with per-node certificates. Firewalls must permit the application HTTPS port and each node's Raft port, and each peer must trust the shared cluster CA for both the Raft transport and authenticated forwarding. Production clustering does not use plaintext.

Quorum behaviour

3/3   -> normal operation
2/3   -> authoritative mutations continue
1/3   -> authoritative mutations fail closed; NO local SQLite fallback

With fewer than a quorum no collection or record mutation commits and no local SQLite fallback occurs; the surviving database is unchanged. Restore a node to return to a quorum and it catches up automatically.

Follower writes

Ordinary mutations may be submitted to any healthy ready follower; the follower authenticates the request, forms the semantic mutation and forwards it to the current leader, then waits for the committed index to be applied locally before returning. While a follower is catching up to the leader, a submitted mutation may transiently return replication unavailable (503). This is fail closed: the mutation is not invisibly committed, and a retry succeeds once the follower is caught up.

Snapshots and recovery

trestle replicate snapshot forces a snapshot on a node. Recovery combines the snapshot with the retained trailing Raft log, so a restarted or offline node rebuilds the exact product state through the latest committed index. Ordinary node restarts, whole-cluster restarts and offline-follower catch-up all recover without manual state copying. The SQLite product database, the Raft log (raft.db) and the snapshot directory are all meaningful parts of a replicated node's durability; do not manually copy or edit them while the cluster is running.

Idempotency

Caller idempotency is consensus-owned: submitting Idempotency-Key with the same semantic intent replays the original committed result on any node, and reusing the key with different content is rejected with a 409 conflict. Idempotency knowledge survives restart and snapshot recovery.

Record preconditions

Record updates and deletes use If-Match with the current record version. A stale precondition is a caller conflict surfaced as a 409, not a cluster failure, and never silently overwrites a newer version.

Peer disable, revoke and rotation

Disabling or revoking a Gantry peer stops replication authorization in both directions and stops delivery of new replicated state to that peer; reauthorizing it allows normal catch-up. Raft voter membership is separate and unchanged by authorization changes. Credential rotation rotates the local outbound credential and bumps the credential version; the current production surface requires a peer to accept the rotated credential (re-pairing re-establishes the pair).

Boundary

Clustering is SQLite-only; enabling replication with the PostgreSQL backend fails closed at startup rather than presenting an unsafe partial mode. The first clustered surface is collection definitions and records only. Replicated replay does not execute webhooks, functions, jobs or email, and files, credentials, sessions and audit/event state are not replicated; those remain node-local or deferred until they have an explicit distributed contract.
