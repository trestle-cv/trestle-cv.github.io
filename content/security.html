Security model

Bound authority at every interface.

Trestle separates administrative control, application identity, service automation, storage and outbound delivery. This page describes implemented controls, remaining deployment boundaries and the evidence still required before a stable release.

Passwords and sessions

Administrator and application passwords are Argon2id hashes with per-password salts. Raw passwords are never stored. Administrator setup is race-safe and closes after the first account commits. Login is rate limited; session identifiers rotate on authentication; logout and account disablement revoke server-side state. Browser mutations require both the session cookie and a matching CSRF token, with origin checks as a second boundary.

Application authorization

List, view, create, update and delete are independent collection operations. Rules are parsed and evaluated on the server; dashboard visibility is not authorization. Individual denials avoid revealing whether a record exists. Service scopes and collection rules both apply, so a broad rule cannot grant a credential a scope it does not possess.

{
  "list": "actor.id != ''",
  "view": "owner_id = actor.id",
  "create": "actor.id != ''",
  "update": "owner_id = actor.id",
  "delete": "false"
}

Data and query safety

User-visible names never become SQLite identifiers. Collections and fields receive stable internal IDs. Filters parse into a bounded typed AST and compile to parameterized SQL. Writes are schema validated, use optimistic versions where required, and rely on SQLite constraints as the final integrity boundary. Batch writes are atomic and bounded to 1,000 records and 8 MiB.

Files and storage

Client filenames remain metadata; generated keys select disk or object-storage paths. Local writes stage then atomically rename, refuse symlinks and reconcile orphaned objects. Downloads require authorization and ranges are bounded. S3 credentials remain process configuration and are never returned to the browser.

Outbound requests and secrets

Webhook endpoints must use HTTPS. Trestle rejects loopback, private, link-local and unspecified destinations, re-resolves DNS at delivery, refuses redirects, bounds response reads and uses finite timeouts. Signing secrets are shown once and encrypted at rest. Service and personal token secrets are shown once and only hashes persist.

Audit, backup and recovery

Administrative and security-sensitive activity emits request-correlated audit facts with structured redaction. Audit rows improve attribution but are not tamper-proof against a host administrator. Backups use SQLite’s consistent backup path, include local-file manifests and can be preflighted before an offline restore. Native exports omit credentials and sessions.

Deployment boundary

Trestle currently binds loopback by default. Until CP22 completes trusted-proxy handling, supported release artifacts and reviewed Caddy/nginx guidance, keep it private or behind a carefully controlled development proxy. TLS, host firewalling, owner-only data directories and operating-system patching remain deployment responsibilities.

Stable-release evidence still outstanding

  • Fuzzing of parsers, filters, archives and protocol boundaries.
  • Race, load, slow-client and restart campaigns.
  • Proxy/header confusion and internet-exposure review.
  • Migration-from-every-supported-version and destructive restore drills.
  • Dependency, artifact, accessibility and threat-model closure.
Report vulnerabilities privately

Do not include credentials, personal data or live deployment details in a public issue. The final disclosure channel and response policy will be published before stable release.
