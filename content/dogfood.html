CP21 tutorial

Build an incident tracker with Trestle

This application was recreated from an empty data directory using only documented HTTP APIs. It exercises the same boundaries a real browser, trusted service and operator use.

Architecture

Browser incident deskSmall same-origin Go frontendTrestle application-user, records and SSE APIsSQLite, local files, event journal and durable jobs

The frontend contains no Trestle package imports. Its Go process serves one embedded HTML file and reverse-proxies /api/ to Trestle, giving the browser a same-origin deployment without exposing administrator credentials.

1. Create the model

The tracker uses an incidents collection plus related updates. Relation values are explicit record IDs; clients query the update collection by incident_id.

{
  "name": "incidents",
  "fields": [
    {"name":"title","type":"text","required":true},
    {"name":"severity","type":"select","required":true},
    {"name":"status","type":"select","required":true,"default":"open"},
    {"name":"summary","type":"text","required":true},
    {"name":"reporter_id","type":"relation","required":true},
    {"name":"resolved_at","type":"datetime"},
    {"name":"context","type":"json","default":{}}
  ]
}

2. Give reporters owner-aware access

{
  "rules": {
    "list": "actor.kind == \"user\"",
    "view": "actor.kind == \"user\"",
    "create": "actor.id == input.reporter_id",
    "update": "actor.id == record.reporter_id",
    "delete": "false"
  }
}

The browser registers and signs in through /api/v1/auth. Administrator cookies never cross into the example application. The updates collection uses the same pattern with author_id.

3. Declare and query incidents

POST /api/v1/collections/incidents/records
Authorization: Bearer $ACCESS_TOKEN
Idempotency-Key: incident-from-monitor-184

{"values":{
  "title":"API latency elevated",
  "severity":"sev2",
  "status":"open",
  "summary":"Public API p95 crossed the threshold.",
  "reporter_id":"usr_...",
  "context":{"region":"ap-southeast-2"}
}}
GET /api/v1/collections/updates/records?filter=incident_id%20%3D%3D%20%22rec_...%22&sort=createdAt&limit=100

4. Attach operational evidence

A scoped service identity receives files:read and records:read. The operator uploads a Markdown runbook bound to the incident record, then the service downloads it through the authenticated file endpoint and verifies its bytes.

curl -X POST "$TRESTLE/api/v1/files" \
  -H "X-Trestle-CSRF: $CSRF" \
  -b admin.cookies \
  -F file=@latency-runbook.md \
  -F collection=incidents \
  -F recordId=rec_...

5. Follow the journal

The browser uses authenticated fetch() streaming rather than putting a bearer token in a query string. The verifier reconnects with Last-Event-ID: 0 and requires a replayed record.created event before passing.

const response = await fetch("/api/v1/realtime", {
  headers: {Authorization: `Bearer ${accessToken}`}
});
const reader = response.body.getReader();

6. Exercise automation honestly

The setup creates and disables a signed webhook target without requiring live DNS. It also configures an AWS Lambda target, emits one incident event, and confirms the durable job records the expected missing-credential retry. The example deliberately ships no cloud credentials and does not misreport provider acceptance.

7. Prove recovery

The verifier creates a database-and-files backup, downloads it, and submits the exact archive to restore preflight. A clean operator can then stop Trestle and follow the offline restore procedure.

go build -o trestle ./cmd/trestle
go build -o incident-tracker ./examples/incident-tracker/cmd/app

Expected identities

The distributed example uses admin@example.com / mudblood for administration and reporter@example.com / reporter7 for the incident desk. Replace both passwords before adapting it to a real deployment.

Boundaries discovered

  • Relation fields currently store record IDs but do not generate target-aware foreign keys or inline expansion.
  • Actual webhook delivery requires resolvable public HTTPS; configuration no longer requires DNS.
  • Actual Lambda acceptance requires operator-supplied AWS credentials.
  • CP22 remains responsible for supported reverse-proxy and internet-facing deployment guidance.
